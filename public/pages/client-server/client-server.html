Client-Server Model

The client-server model describes how clients and servers communicate over a network.

A client sends a request to a server, and the server processes the request and sends a response back.

A web browser is an example of a client, while an Express application can act as a server.

A server can also act as a client when it sends requests to another server.

Example of Client-Server Communication

app.get('/greetings', (req, res) => {
    res.send('Hello from the server!');
});

When a client sends a GET request to /greetings,the Express server receives the request and sends a response containing the message "Hello from the server!". The client then receives the response.

Server Acting as a Client

A server can also act as a client when it sends requests to another server. An example of this is the /proxy endpoint, where Express uses fetch() to retrieve data from Google before responding to the original client. See the Fetch API example

HTTP Requests and Responses

HTTP (Hypertext Transfer Protocol) is used for communication between clients and servers.

The client sends an HTTP request, and the server returns an HTTP response.

HTTP Request

An HTTP request contains a method, a url path and headers. It can also contain a body with data sent to the server.

HTTP Response

An HTTP response contains a status code and headers. It can also contain a body with data such as HTML or JSON.

For more information about HTTP methods and status codes, see the REST API documentation.

URLs

URL stands for Uniform Resource Locator.

It specifies the address of a resource on the web.

A URL can contain a protocol, domain, path and query parameters.

Example: https://www.google.com/search?hl=en&q=what%20doth%20life

  • Protocol: https = specifies how the client communicates with the server.
  • Protocol separator: :// = separates the protocol from the rest of the URL.
  • Subdomain: www = a subdomain of google.com.
  • Domain: google.com = the domain name.
  • Top-level domain: .com = the last part of the domain name.
  • Path: /search = identifies the requested resource.
  • Query string: ?hl=en&q=what%20doth%20life = contains the query parameters.
  • Query parameters: hl=en and q=what%20doth%20life = key-value pairs that provide additional information.

Path Variables

A path variable is a dynamic value in a URL path. For example, in /search/1, the value 1 can be used as a path variable.

Fetch API

The Fetch API allows JavaScript to make HTTP requests and receive responses from a server.

The fetch() function returns a Promise, which represents a result that may become available later.

fetch('https://example.com')
    .then(response => response.text())
    .then(data => console.log(data));

In this example, fetch() sends a GET request. The first .then() reads the response body as text, and the second .then() logs the result to the console.

Fetching Data from Another Server

Fetch can also be used in Node.js to retrieve data from another server. In this example, an Express endpoint fetches a webpage and sends the content back to the client.

app.get('/proxy', (req, res) => {
    fetch('https://www.google.com/')
        .then(response => response.arrayBuffer())
        .then(buffer => {
            const decoder = new TextDecoder('ISO-8859-1');
            res.send(decoder.decode(buffer));
        });
});

When a client sends a GET request to /proxy, the Express server uses fetch() to request a webpage from Google. The response is read as binary data using response.arrayBuffer(). Then TextDecoder converts the data into text using the specified character encoding (ISO-8859-1). And then res.send() sends the decoded text back to the client.

CORS

CORS stands for Cross-Origin Resource Sharing. It is a browser security mechanism that controls whether JavaScript from one origin can access responses from another origin.

An origin consists of a protocol, domain and port.

For example:

http://localhost:3000 and http://localhost:8080

They are different origins because they use different ports.

CORS restrictions are enforced by browsers.

Server-side requests are not subject to the same browser restrictions, which is one reason SSR can help avoid certain CORS issues.

XSS

XSS stands for Cross-Site Scripting. It is a security vulnerability where an attacker injects malicious code into a webpage, causing it to execute in another user's browser.

Preventing XSS

One way to reduce the risk of XSS in the frontend is to use textContent instead of innerHTML when displaying untrusted user input.

textContent treats the input as text

while innerHTML interprets it as HTML.

const userInput = '<script>alert("XSS")</script>';

element.textContent = userInput;

In this example, the input is displayed as text instead of being interpreted as HTML. On the backend, user input should also be handled safely, for example by using appropriate sanitization when HTML content is allowed.

Escaping HTML Characters

Another way to prevent XSS when inserting untrusted text into HTML is to escape special characters. This sanitizeXSS() function can be used to replace special characters with HTML entities.

export function sanitizeXSS(string) {
    return string
        .replaceAll('&', '&amp;')
        .replaceAll('<', '&lt;')
        .replaceAll('>', '&gt;')
        .replaceAll('"', '&quot;')
        .replaceAll("'", '&#39;')
        .replaceAll('`', '&#x60;')
        .replaceAll('/', '&#x2F;');
}

The function replaces special characters with HTML entities. This helps prevent untrusted input from being interpreted as HTML markup when inserted into HTML text content. But different contexts may require different security measures.
