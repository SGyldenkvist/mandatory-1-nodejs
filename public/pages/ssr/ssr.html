Server-Side Rendering

SSR stands for Server-Side Rendering.

With SSR, the server generates or assembles the HTML before sending it to the client.

The browser receives HTML that already contains the content of the page.

Client-Side Rendering

CSR stands for Client-Side Rendering.

With CSR, JavaScript runs in the browser and generates or updates the content of the webpage.

The server can send an HTML document, while JavaScript is responsible for rendering the content in the browser.

SSR vs. CSR

SSR and CSR are two different approaches to rendering webpages.

Server-Side Rendering (SSR)

  • The server generates the HTML before sending it to the browser.
  • The initial content can be displayed without waiting for client-side JavaScript to render it.
  • SSR requires server resources to generate the HTML.
  • SSR can be beneficial for SEO because the content is included in the HTML response.

Client-Side Rendering (CSR)

  • JavaScript generates or updates the content in the browser.
  • The browser may need to download and execute JavaScript before displaying the main content.
  • CSR moves more of the rendering work to the client.
  • SEO can be more challenging if the content depends on JavaScript execution.

Search Engine Optimization (SEO)

SEO stands for Search Engine Optimization. It is about making a website easier for search engines, such as Google, to find, understand and show in search results.

SSR can be beneficial for SEO because the HTML sent from the server already contains the page content.

With CSR, some content is generated by JavaScript in the browser. This can make it more challenging for search engines to access and index the content.

File Reading

Node.js can read files from the file system using the built-in fs module.

This can be used to read HTML files on the server before sending their content to the client.

Synchronous File Reading

readFileSync() reads a file synchronously. This means that Node.js waits for the file to be read before continuing with the next line of code.

import fs from 'fs';

const frontpage = fs.readFileSync('./public/pages/frontpage/frontpage.html', 'utf8');

In this example, readFileSync() reads the HTML file and returns its content as a string because the encoding is set to utf8.

This is blocking, so JavaScript execution pauses until the file has been read.

Asynchronous File Reading

readFile() reads a file asynchronously. This means that Node.js can continue executing other code while waiting for the file to be read.

import fs from 'fs/promises';

const frontpage = await fs.readFile('./public/pages/frontpage/frontpage.html', 'utf8');

In this example, readFile() returns a Promise. The await keyword waits for the Promise to resolve before assigning the file content to frontpage.

This is non-blocking, so Node.js can handle other work while waiting for the file.

Templating

Templating can be used to reuse HTML components across multiple pages.

Instead of repeating the same header and footer in every HTML file, they can be stored in separate files and combined with the page content on the server.

Reusable HTML Components

A webpage can be constructed from three parts:

  • Header - shared content at the top of the webpage.
  • Page - the content of the individual page.
  • Footer - shared content at the bottom of the webpage.

Constructing a page

In the following example we used a templating engine to combine a header, page content and footer into one HTML document.

import fs from 'fs';

export function constructPage(page, options = {}) {
    const header = readPage('public/components/header/header.html');
    const footer = readPage('public/components/footer/footer.html');

    return header
        .replace('{{CSS_LINKS}}', options.cssLinks || "")
        .replace('{{JS_LINKS}}', options.jsLinks || "")
        .replace('{{TAB_TITLE}}', options.tabTitle || "Planter")
     + page
     + footer;
}

export function readPage(path) {
    return fs.readFileSync(path, 'utf-8');
}

readPage() reads an HTML file and returns its content as a string.

constructPage() reads the shared header and footer, replaces placeholders in the header and combines them with the page content.

The options object can be used to provide CSS links, JavaScript links and a page title. If no values are provided, default values are used.

Using the Templating Engine

In pages.js, we used readPage() to read the HTML content of different pages and constructPage() to combine the content with the shared header and footer.

import { constructPage, readPage } from "./templatingEngine.js";

const frontpage = readPage('public/pages/frontpage/frontpage.html');
const about = readPage('public/pages/about/about.html');

export const frontpagePage = constructPage(frontpage, {
    cssLinks: `<link rel="stylesheet" href="/pages/frontpage/frontpage.css" />`,
    jsLinks: `<script src="/assets/js/escapeHTML.js"></script>`
});

export const aboutPage = constructPage(about, {
    tabTitle: "Planter | About"
});

export const contactPage = constructPage(about);

frontpagePage includes additional CSS and JavaScript links.

aboutPage uses a custom page title.

contactPage uses the default options because no options object is provided. In this example, it also reuses the about page content.

The resulting HTML strings can then be sent to the client through Express routes.

Templating and Performance

The templating engine uses readFileSync() to read the header and footer.

Because readFileSync() is synchronous, it blocks JavaScript execution while reading the files.

In this example, the pages are constructed when pages.js is loaded, rather than being reconstructed for every HTTP request.

This avoids reading the same HTML files again for every request, but changes to the files require the pages to be reconstructed before they appear in the response.
